Keep tightly related statements together; do not add a blank line after every statement. Apply this convention to source code, tests, and configuration, excluding generated files. ESLint derives literal guards from the canonical application constants; keep those guards and their regression checks enabled.

## Product

car-log tracks personal vehicle expenses. Each user can own multiple vehicles, record liquid-fuel fill-ups or EV charging, record other categorized expenses, and inspect costs and consumption over time.

Required capabilities:

- Authentication and registration with roles `USER` and `ADMIN`. Administrators have normal user capabilities plus user listing, registration approval, blocking, and account deletion.
- Vehicles: required manufacturer/model and a nonempty list of fuel/energy types; optional license plate, first-registration calendar date, color, VIN, and one picture; created/updated timestamps.
- Two expense groups: `FUEL` and `OTHER EXPENSES`. Expense types such as oil, brakes, and tires belong to the second group; users can add types to a codelist.
- Refueling/charging: vehicle, quantity, price per unit or total price, odometer, date/time, full-tank/full-charge flag, and a flag indicating missing preceding records.
- Other expenses: vehicle, expense type, price, odometer, date/time, and comment.
- Statistics: odometer information, fuel costs, other costs, combined costs, totals per expense type, fuel-price history, other-expense charts, and consumption per 100 km. Support preset and custom date ranges.

## Authentication requirements

- Keep role and account status separate; approval/blocking are not roles.
- Use Prisma-generated `UserRole`, `UserStatus`, and `FuelType` values from `src/generated/prisma/enums.ts` for comparisons, database writes, Zod schemas, result types, and fixtures. Do not duplicate their string values or define parallel enums. Use `z.enum(UserRole)` for role validation and `typeof UserStatus.ACTIVE` when a literal member type is needed. The standalone enums module is safe for shared/client imports; do not import PrismaClient for enum values. ESLint rejects hardcoded role/status/fuel literals in application code and tests; keep this guard enabled. Generated files and committed SQL migrations are excluded.
- Users require unique email and username; firstName and lastName are optional. Registration normalizes email by trimming and lowercasing it. Usernames must be 3–30 lowercase ASCII letters/digits; uppercase, whitespace, and `@` are rejected. Future login accepts username or email without ambiguous matches.
- Agreed registration policy: the first successful registration becomes an `ACTIVE` `ADMIN`; later registrations start as `PENDING` `USER` accounts and require administrator approval before login.
- Never allow public registration input to assign role/status. Implement first-admin provisioning atomically on the server, with a persistent bootstrap marker so deleting all users cannot reopen automatic admin registration. Do not rely on an unprotected user-count check.
- Agreed password policy: 10–128 ASCII characters, at least one `a-z`, one `A-Z`, and one digit. Optional supported special characters are `*$#&,.%@-_~|\/!?^`. Reject all whitespace and unsupported characters; never trim passwords.
- Use Argon2id through Node's built-in asynchronous `crypto.argon2` API (requires Node >=24.7), not a separate hashing dependency. Store a PHC string with version, settings, random salt, and hash. New-hash targets come from `ARGON2_MEMORY`, `ARGON2_PASSES`, and `ARGON2_PARALLELISM` in `.env` (defaults/recommended baseline: 65536 KiB, 3, 1). Salt/hash sizes stay 16/32 bytes. Supported integer costs are memory 19456–262144 KiB, passes 2–10, and parallelism 1–4. Use cryptographically random 32-byte session tokens and store only their SHA-256 hashes. Never implement cryptographic primitives manually.
- Password hashing also requires `PASSWORD_PEPPER`, a server-only random 32-byte secret stored as 64 hexadecimal characters in `.env` or injected securely. Pass it through Argon2's `secret` parameter; never store it in hashes, the database, logs, bundles, or committed configuration. Fail closed if missing/malformed. Tests generate their own pepper. Preserve the pepper across deployments; rotation and existing unpeppered hashes require an explicit password migration/reset strategy.
- `verifyPassword` compares exact input with `timingSafeEqual` using the hash's stored cost settings within supported bounds, independently of today's targets. Do not remove historical profile support just because new-hash targets change. There is no unpeppered fallback; missing/malformed pepper configuration is an operational error.
- Password-only operations can use `verifyUserPassword`; login uses `verifyAndUpgradeUserPassword` to retain proof of the verified hash, then locks/rechecks the account before issuing a session. Both conditionally persist a fresh hash when cost targets differ. Never rehash before successful verification, overwrite a concurrent password change, or confuse password verification with account-status authorization/session creation.
- Sessions have a sliding 14-day idle expiry: every successful authenticated session check renews the database expiry and cookie to 14 days from that check. Tokens rotate on login; renewal retains the token to avoid browser-tab races. There is no absolute lifetime cap while the user remains active. Use `getCurrentSession` on protected operations; never authorize from cached GUI user data.
- Logout deletes the current device session before clearing its cookie. Account status changes away from ACTIVE revoke all sessions through a database trigger; deletion also cascades. Unblocking must not revive old tokens. Session creation rechecks status and the verified password hash under a user-row lock.
- Use the host-only `car_log_session` cookie with HttpOnly, SameSite=Lax, Path=/, a 14-day Max-Age/Expires, and Secure in production (requires HTTPS). Protect state-changing requests against CSRF, verify the framework's protections, and configure production traffic limits in Traefik.
- Login failures for unknown identifiers, incorrect passwords, and inactive accounts share the same INVALID_CREDENTIALS response. Always perform Argon2 work for missing/inactive accounts; avoid a cheap user-existence path and never distinguish the failing credential in responses. Exact network/database timing equality is not guaranteed.
- Do not store authentication tokens in browser local storage. JWT is not the default for this same-origin browser app; revisit it only for a concrete integration requirement.

- Authenticated users may update only their own profile. Email/username/password changes require the current password, apply atomically, revoke all sessions, and rotate the current browser cookie. Names-only edits keep sessions. Never accept user ID, role, status, or email verification state in profile input.
- Email verification uses SMTP via Nodemailer and Handlebars HTML with a text fallback; Slovak copy stays in translation bundles. MailDev in Compose captures development messages. Verification tokens are random, hashed in the database, single-use, valid for 24 hours, and bound to the current address. Address changes clear verification and replace outstanding tokens. Verification does not approve pending accounts or gate normal login. Forgotten-password reset requires an ACTIVE account with a verified current email. Send mail after database commit and report delivery failures without claiming the saved change was rolled back.

- Forgotten-password requests accept username/email and return a generic accepted result without account/delivery details. Keep account lookup/SMTP outside the response in background work. Reset links use random hashed single-use tokens, expire after one hour, and are invalidated by replacement, credential/address changes, verification removal, blocking, or deletion. Reset under a user-row lock, recheck all conditions after hashing, and atomically change the password, consume the token, and revoke all sessions. Never auto-login on reset. Preserve CSRF protection. Recovery forms use the library's `useAppForm` and registered input/submit components with Zod validation. Wrap synchronous Zod validators once with `translatedSchema(schema, t)` at the TanStack Form boundary. Let tope-ui inputs/selects read touched state and localized errors from their field context; do not repeat `error` props or field-error subscription logic. Backend validation keys remain untranslated.

## Fuel records

- Phase 5 backend and GUI are implemented. The authenticated `/fuel` route is the combined fuel/charging table, with `/fuel/new` and `/fuel/$recordId` forms. Use JavaScript numbers for quantities, prices, odometers, calculations, and RPC values. Keep the existing PostgreSQL NUMERIC columns; convert Prisma Decimal fields to numbers when reading them.
- The fuel table selects one vehicle, hides vehicle selectors and vehicle name/label text when only one exists, and filters fuel types optionally. Show the fuel-type filter and its label only when the selected vehicle has multiple fuel types; ignore stale fuel-type URL filters for a single-fuel vehicle. Use tope-ui Table server pagination and row-click editing with a rightmost delete action. Keep table action columns sticky on the right with an opaque background, border, and shadow using the Table stories' additionalClassName pattern, for desktop tables. Provide compact `renderMobileRow` layouts below the tablet breakpoint, with units and metadata beside values and a dots-only `TableRowMenu` for actions. New records default to full tank/full charge; editing preserves the saved flag. Record forms use registered Select, DateTimeInput, Switch, and numeric Input fields (`type="number"`, number/null form values).
- Use Europe/Bratislava consistently for date/time display and local-input conversion. Preserve unchanged instants, including milliseconds. Reject nonexistent spring times; repeated autumn times require an explicit occurrence. Use the shared tested helpers, not the device timezone.
- Currency is EUR. Units are km, litres for petrol/diesel/LPG, kg for CNG, and kWh for electricity. Accept exactly one pricing mode: paid total or unit price. Calculate a paid total from quantity × unit price using half-up cent rounding; derive the stored effective unit price from the authoritative total. Do not treat a rounded unit price as the authoritative cost.
- Each vehicle + fuel type is an independent timeline. The vehicle/fuel/timestamp combination is unique; odometer must be strictly between chronological neighbours in that timeline. Recalculate old and new timelines when moving a record; write only changed derived caches. Clear caches before making a record partial/electric so database constraints remain valid throughout the transaction.
- Vehicle/account deletion cascades to fuel records. Do not remove a vehicle fuel type while records still use it; users must explicitly move/delete those records first. Never silently delete fuel history as part of changing vehicle fuel types.

## Statistics and charts

- Phase 7 provides an ownership-scoped `getStatistics` GET RPC and the authenticated `/statistics` page, linked from the Header. The welcome/vehicle overview is the home screen; fuel tracking is at `/fuel`. Hide the vehicle selector and label when only one vehicle exists.
- Report one vehicle at a time. Presets are all history, this/last month, this/last year, and an inclusive custom calendar-day range. Resolve boundaries in Europe/Bratislava, with a half-open UTC interval from local midnight to the day after the selected end. Custom inputs follow the UI's 1900–2100 year range.
- Attribute paid costs to purchase/expense timestamps. Consumption includes valid full-to-full intervals whose ending fill-up falls in the range, using stored interval quantities/distances even when the baseline or intermediate partial purchase is earlier. Divide total valid quantity by total valid distance; never average cached consumption rates. Exclude missing/invalid intervals and show coverage/unavailable explanations. EV energy/costs are shown without consumption estimates.
- Latest recorded odometer is from all history, ordered by event timestamp across fuel and other expenses, using the higher reading for simultaneous events. Label its all-history scope. Do not sum readings, infer lifetime distance, or combine fuel-specific consumption distances.
- Statistics renew sessions in a short transaction, then recheck session validity and ownership in a read-only RepeatableRead transaction. Do not call the locking/renewing session helper inside the report transaction. Keep owner-row locks for mutations.
- Aggregate in PostgreSQL and return numeric values using double precision casts. Use JavaScript numbers for all calculations and responses. Round displayed statistics/tooltips to at most two decimal places through the shared exponent-shifting number helper and Slovak Intl formatting. Keep statistics ratios unrounded until display. Price averages are weighted by purchased quantity. Category totals include archived categories and current names.

## Expense and statistics correctness

- Keep PostgreSQL NUMERIC storage and use JavaScript number arithmetic in the application. Use the shared roundNumber helper for money and derived caches at their storage precision; do not add Decimal/BigInt arithmetic or decimal-string RPC contracts.
- Distinguish liquid fuel quantities from EV energy. Show L/100 km and kWh/100 km separately; do not combine incompatible quantities into one consumption average.
- Do not infer EV consumption from two state-of-charge flags alone: purchased charging energy may include losses and does not establish energy used between charges. Agree on the estimator and label before implementation.
- For liquid fuel, calculate consumption only over valid full-to-full intervals. Include intermediate partial fill-ups; exclude the starting fill-up's quantity. Missing records invalidate affected intervals. Exclude zero/negative-distance intervals and show unavailable results rather than invented values.
- Calculate aggregate consumption from total valid quantity divided by total valid distance, not an unweighted mean of interval consumption values.
- Derive history in chronological order and recalculate affected intervals after edits/deletions. Preserve the agreed independent fuel timelines, timestamp uniqueness, strict odometer ordering, and missing-history rules.
- Distinguish latest recorded odometer from distance traveled in a selected period. Never sum odometer readings or assume the first recorded odometer is zero.
- Agree on currency and unit policy before totals; never sum different currencies without an explicit conversion policy.
- Store instants consistently and apply explicit timezone/date-range boundaries. Specify which date controls costs and which interval controls consumption in filtered reports.
- Treat vehicle registration date as a calendar date, distinct from expense timestamps.
